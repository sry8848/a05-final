# 面试流程策略（简化版 V2）

## 1. 设计目标

- 在可控复杂度下实现：题目难度匹配、项目深挖、知识域覆盖、过程可解释。
- 优先“先跑通再增强”，避免一次性引入过重并发控制与状态协议。

---

## 2. 核心调整（对应评审结论）

1. 岗位、年限分层、深度等级均使用枚举。
2. 增强项目信息结构，防止后续追问丢失上下文。
3. 取消重型 `interview_constraints`，只保留最小必要约束。
4. 显式配置题型数量配额（如自我介绍 1、场景题 3）。
5. 知识域统一使用 `domain_id` 传递，展示层再映射中文名。
6. 取消硬 `question_budget`，改为“问透即降权/切域”规则。
7. 版本控制降级为最小可实现：会话串行 + `attempt_id` 幂等。
8. 不生成能力快照，状态账本作为唯一过程状态表达。
9. 上下文读取固定为：最近 `x` 题完整 `Q/A`，更早历史题仅问题文本。

---

## 4. 状态账本（后端唯一可信状态）

```json
{
  "ledger_id": "ledger_001",
  "session_id": "s_123",
  "overall_status": "IN_PROGRESS",
  "active_project_id": "p_order_risk",
  "domain_states": [
    {
      "domain_id": "java_core",
      "target_depth": "L4",
      "current_depth": "L3",
      "status": "IN_PROGRESS",
      "saturated": false,
      "evidence_refs": ["q_003", "q_006"]
    }
  ],
  "question_mix_progress": {
    "INTRO": 1,
    "PROJECT_DEEP_DIVE": 2,
    "SCENARIO": 1,
    "PRINCIPLE": 2,
    "BEHAVIORAL": 0
  },
  "asked_total": 6,
  "last_attempt_id": "a_006"
}
```

### 4.1 状态机

- `UNASKED -> IN_PROGRESS -> COMPLETED`
- 异常分支：`UNASKED/IN_PROGRESS -> SKIPPED`
- `saturated=true` 表示该域已问透，策略层默认降权。

### 4.2 问透判定规则（替代 question_budget）

满足以下条件可判定“问透”：

1. `current_depth >= target_depth`
2. 最近 2 次同域回答质量分不低于阈值（如 `>= 75`）
3. 关键追问点已覆盖（由 evidence 标记）

判定问透后：

- 该域 `saturated=true`
- 后续优先切换未饱和知识域或项目维度

## 5. 服务职责（简化但清晰）

## 5.1 `planner`

- 输入：岗位、年限、简历项目信息
- 输出：主考纲（含题型配额、domain、projects）
- 约束：只初始化，不参与逐题更新

## 5.2 `answer_evaluation_and_next_question_decision`

- 输入：
- 本次回答
- 最近 `x` 题完整 `Q/A`
- 更早历史题仅问题文本
- 主考纲
- 当前状态账本
- 输出：
  - 本题评估
  - 账本 patch（如深度变化、是否问透、题型进度）
  - 下一题类型与方向
  - RAG 检索意图

> 当前阶段保留一体化服务，减少联调复杂度；不引入异步能力快照。

## 5.3 `question_generation`

- 输入：下一题策略 + RAG 结果
- 输出：题目文本（流式）
- 约束：仅生成题目，不直接修改账本

---

## 6. 每题处理流程（最小可实现）

1. 后端收到回答，生成 `attempt_id`（全局唯一）。
2. 幂等校验：若 `attempt_id` 已处理，直接返回已有结果。
3. 按固定规则组装上下文：
   - 最近 `x` 题：完整 `Q/A`
   - 更早历史题：仅问题文本
   - 主考纲 + 当前状态账本 + 本次回答
4. 调用 `answer_evaluation_and_next_question_decision`。
5. 后端应用账本 patch（单会话串行处理，避免并发冲突）。
6. 执行 RAG 检索（正向 + 反证）。
7. 调用 `question_generation` 流式出题。
8. 记录审计日志（模型版本、prompt 版本、耗时、token）。

> 本阶段不引入复杂 `version` 乐观锁与重 patch 冲突处理；当出现多端并发答题需求时再升级。

## 7. 语音输入协议

前端可通过 WebSocket 直连云厂商 ASR，后端接收结构化结果：

```json
{
  "attempt_id": "a_007",
  "question_id": "q_007",
  "asr": {
    "is_final": true,
    "segments": [
      {"text": "我先做容量估算", "start_ms": 0, "end_ms": 1200, "pause_ms_after": 300},
      {"text": "再按I/O占比调整线程池", "start_ms": 1500, "end_ms": 3300, "pause_ms_after": 0}
    ],
    "revisions": [
      {"from": "线程越多越好", "to": "线程并不是越多越好"}
    ]
  }
}
```

规则：

- 仅 `is_final=true` 进入正式评估。
- 中间帧仅用于前端展示，不进入主评估流水。

---

## 8. 结束产物

面试结束生成两层结果：

- 总体评价：匹配度、亮点、风险项、录用建议
- 明细评价：按题型与 `domain_id` 输出得分和证据

---

## 9. 上线前检查清单

- 题型配额是否满足（如 INTRO 必须为 1）
- `domain_id` 与展示映射表是否一致
- 问透规则是否生效（避免单域过问）
- `attempt_id` 幂等是否覆盖重试场景
- 最近 `x` 题是否传入完整 `Q/A`
- 更早历史题是否只传问题文本
- 语音 `is_final` 过滤是否正确

该版本强调低复杂度可落地，适合作为第一阶段实现基线。
