## 3. 详细冲突与建议

### D1. MVP 登录能力边界不一致

**冲突来源**
- `product-scope.md`：MVP 仅强调邮箱注册 + 邮箱验证码登录；密码登录、手机号登录后置（P2）。
- `api-design.md`：将邮箱密码登录、手机验证码登录/发送均标记为 `[MVP]`。
- `page-list.md`：登录页接口映射包含手机登录接口。
- `auth-pages-plan.md`：登录 UI 为邮箱密码 + 邮箱验证码，手机验证码后续迭代。

**影响**
- 前后端接口范围无法冻结；测试用例与排期会失真。

**可选方案**
- **A（收敛 MVP）**：MVP 只保留邮箱验证码登录；密码/手机登录全部移到非 MVP。
- **B（扩展 MVP）**：MVP 保留邮箱验证码 + 邮箱密码；手机登录后置。
- **C（全开 MVP）**：邮箱验证码 + 邮箱密码 + 手机验证码全部 MVP。

**建议**
- 建议选 **B**：平衡体验与复杂度，和现有登录页计划最一致。

我选择B
---

### D2. 注册流程是否必须验证码

**冲突来源**
- `api-design.md`：注册需先发送 `scene=register` 验证码，再提交 `email+code+nickname+password`。
- `auth-pages-plan.md`：注册页字段未包含验证码，仅 email/nickname/password/confirmPassword。

**影响**
- 注册页字段与后端入参不一致，联调必崩。

**可选方案**
- **A**：注册强制验证码（安全优先）。
- **B**：注册不强制验证码（实现更快，风控后补）。

**建议**
- 建议选 **A**，并把注册页补齐验证码输入与发送按钮。

我选择A
---

### D3. 面试主流程顺序冲突（Prepare / DeviceTest）

**冲突来源**
- `page-list.md`、`development-plan.md`：`Prepare -> 创建会话 -> DeviceTest -> Loading -> Interview`。
- `product-scope.md` 的流程图：`DeviceTest -> Prepare -> Loading -> Interview`。

**影响**
- sessionId 何时生成、页面跳转逻辑、埋点口径都会错位。

**可选方案**
- **A**：先 Prepare 创建会话，再 DeviceTest（当前多数文档采用）。
- **B**：先 DeviceTest，再 Prepare 创建会话。

**建议**
- 建议选 **A**，因为 DeviceTest 页已定义需要携带 `sessionId`。

我选择A

---

### D4. Loading 阶段是否生成第一题

**冲突来源**
- `product-scope.md`：Loading 仅做 Planner + 状态账本初始化，“不生成具体题目”。
- `prompt-strategy.md`：存在在 planning 阶段生成第一题的表述。
- `api-design.md`、`development-plan.md`：当前已收敛为“Loading 完成考纲与状态账本初始化，首题获取策略待 D4 决策”。

**影响**
- 面试页首题获取方式不一致，导致前端状态机和后端编排冲突。

**可选方案**
- **A**：Loading 结束前生成第一题（减少一次请求与等待）。
- **B**：Loading 只生成考纲，进入面试页后再请求首题。

**建议**
- 当前先维持 **TBD**，后续单独拍板；其余文档统一按“待 D4 决策”处理，避免实现提前绑定。

暂时搁置，将有较大变化

### D5. 专业模式输入方式冲突

**冲突来源**
- `product-scope.md`：专业模式“只允许语音输入”。
- `page-list.md`：同一章节既写“专业模式语音录入”，又写“文本输入框（练习模式 / 专业模式备选）”。
- `api-design.md`：`submit-and-next` 带 `answerMode`，未明确专业模式是否禁用 text。

**影响**
- 前端交互与后端校验策略不统一。

**可选方案**
- **A**：专业模式强制语音，仅保留转写编辑能力。
- **B**：专业模式默认语音，但允许降级文本输入（设备失败兜底）。

**建议**
- 已按你的决策收敛为 **A**：专业模式强制语音输入，不提供文本兜底输入。

我选择A
---

### D6. 简历“文本粘贴”能力与 API 缺口

**冲突来源**
- `product-scope.md`：MVP 支持“文本粘贴 + 文件上传”两种简历来源。
- `db-schema.md`：`resumes.source_type` 支持 `text/file`。
- `api-design.md`：仅定义上传/编辑/设默认等接口，缺少直接“文本创建简历”接口。

**影响**
- 产品承诺能力在 API 层不可达，前端只能曲线实现。

**可选方案**
- **A**：新增 `POST /api/v1/resumes/text`。
- **B**：复用 `POST /api/v1/resumes/upload`，允许传 text（语义混乱，不建议）。
- **C**：删掉“文本粘贴”需求，仅保留文件上传。

**建议**
- 建议选 **A**，语义清晰，和数据模型一致。

我选择C

---

### D7. 题量控制权归属

**冲突来源**
- `product-scope.md`：用户可设置 `maxQuestionCount`（默认 10，范围 5-20），最少 3 题。
- 你当前方案：题量由 AI 与后端内置规则共同控制，前端不暴露题量参数。
- `api-design.md`、`db-schema.md`：已收敛为不暴露 `maxQuestionCount`，也不再保留对应会话字段。

**影响**
- 若产品文档不修正，产品、前端、测试仍可能误以为用户可以配置最大题量。

**可选方案**
- **A**：补充 `maxQuestionCount` 入参与会话字段，允许用户配置。
- **B**：由后端完全内置，不暴露给前端。

**建议**
- 已按你的决策收敛为 **B**：题量由后端 AI 与内置规则控制，前端不暴露配置项；产品文档需后续同步修正。


我选择B,最大题目数量只由ai决定，后端内置范围规定

### D8. 成长中心与个人设置职责边界冲突

**冲突来源**
- `product-scope.md`：成长中心包含“头像、昵称、基础资料编辑”。
- `page-list.md`、`development-plan.md`：成长中心与设置页隔离，资料编辑放 `/settings`。

**影响**
- 前端页面职责不清，重复开发风险高。

**可选方案**
- **A**：成长中心只展示，编辑统一跳 `/settings`。
- **B**：成长中心内直接编辑，`/settings` 缩减为安全配置页。

**建议**
- 建议选 **A**，信息架构更清晰。

我选择A
---

### D9. 登录页文档内部冲突（`page-list`）

**冲突来源**
- `page-list.md` 登录页核心模块写“登录方式切换 Tab（邮箱验证码）”，却又在字段中包含 `password/phone/loginType`，接口映射也包含手机登录。

**影响**
- 前端实现人员无法依据单一文档准确落地。

**可选方案**
- **A**：登录页明确仅两种：邮箱密码 + 邮箱验证码（手机后置）。
- **B**：三种登录都开放（邮箱密码/邮箱验证码/手机验证码）。

**建议**
- 建议与 D1 保持一致；若 D1 选 B，则 D9 也选 A（即两种登录）。

我选择A,但要预留后续开发能力
