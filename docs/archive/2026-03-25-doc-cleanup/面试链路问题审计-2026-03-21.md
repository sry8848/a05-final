# 面试链路问题审计

审计时间：2026-03-21

## 审计范围

本次只看当前仓库里真实在跑的面试链路，不按旧文档想当然：

- 前端：`frontend/src/components/InterviewPage.vue`、`frontend/src/App.vue`、`frontend/src/utils/interviewDecision.js`
- 后端入口：`backend/src/main/java/com/a05/aiinterview/interview/service/InterviewService.java`
- 编排与状态：`PlannerOrchestrationService`、`PlannerDomainNormalizationService`、`StateLedgerInitService`、`AnswerSubmitService`、`StateLedgerPatchService`
- 出题流：`QuestionStreamService`、`SseDoneEvent`
- 辅助链路：`InterviewSkipService`

## 当前实际链路

### 主链路

1. 前端创建会话，后端进入 `planning`。
2. `PlannerOrchestrationService` 异步调用 `planner`，再做知识域归一化、组装 `syllabus`、初始化 `ledger`、生成首题。
3. 前端轮询 `GET /interviews/{sessionId}`，拿到 `firstQuestionJson` 后开始面试。
4. 用户回答后调用 `POST /interviews/{sessionId}/attempts`。
5. 后端调用 `evaluation-decision`，写 attempt、写账本，然后前端再用 `streamAttemptId` 调 `GET /questions/stream`。
6. `QuestionStreamService` 再根据 attempt 里的 `evaluationJson` 组装下一题生成输入，流式出题并落库。
7. 结束后走 `finish` + `report-generation`，单题详细评估由事件异步触发。

### 并存的旁路

- `skip-and-next` 不是主链路的一部分，而是单独伪造一份 `EvaluationDecisionOutput`
- 单题模式至少有两套：
  - 后端 `CreateInterviewRequest.singleQuestion*`
  - 前端从问答库直接进入 `startSingleQuestionInterview()` 的本地链路

## 核心结论

当前最大问题不是“链路没打通”，而是：

1. 程序仍在多处擅自补写、推断、映射 AI 语义结果。
2. 新旧链路、新旧枚举、新旧状态源同时存在，导致系统表面统一，内部却是双轨。
3. 前端仍然保留本地造分、本地造题元数据、本地单题面试这些旧习惯，持续污染主链路。

下面按优先级列问题。

## P0 问题

### 1. 前端仍保留旧 `evaluationSignal` 兼容，旧语义没有删干净

证据：

- `frontend/src/utils/interviewDecision.js:1-31`
- `frontend/tests/interview-decision.test.js`

现状：

- `normalizeInterviewDecision()` 优先读新字段 `decision`
- 但如果没有，就继续把旧字段 `evaluationSignal` 映射成 `followup/rescue/broaden/wrapup`
- 测试还在显式锁定这套旧映射

问题：

- 这意味着新链路没有真正收口，旧响应结构依然是被支持的正式输入
- 一旦后端有人偷懒继续吐旧字段，前端不会报错，只会静默兼容
- 这正是“旧链路不删除”的典型后患

建议：

- 直接删除 `evaluationSignal` 兼容逻辑和对应测试
- 前端只接受当前正式契约字段；缺字段就报错，不再兜底兼容旧响应

### 2. 前端在本地按 `decision` 造分、算总分、拼反馈，直接改写了 AI 结果语义

证据：

- `frontend/src/utils/interviewDecision.js:8-36`
- `frontend/src/components/InterviewPage.vue:2348-2355`
- `frontend/src/components/InterviewPage.vue:2540-2565`

现状：

- 单题分数来自 `mapDecisionScore(decision)`
- 总分来自前端自己平均这些造出来的分数
- `beatPercent` 还带随机数
- `feedback` 也是前端根据区间硬编码生成

问题：

- `decision` 是流程动作，不是评分结果
- 这不是“校验/拒收/降级”，而是程序在擅自把流程信号改写成评分结论
- 用户最终看到的即时结果并不来自 AI 评估，也不来自后端报告，而是前端造值

建议：

- 删除基于 `decision` 的本地打分逻辑
- 没有后端正式分数时，只显示“报告生成中/结果待生成”，不要给伪分数

### 3. `PlannerDomainNormalizationService` 会主动补齐知识域，程序在改写 planner 语义

证据：

- `backend/src/main/java/com/a05/aiinterview/interview/engine/PlannerDomainNormalizationService.java:19-84`

现状：

- 非法域会被过滤，这部分还算校验
- 但当 planner 输出域数量不足时，程序会强行回填到至少 `MIN_PLANNER_DOMAINS = 5`

问题：

- “过滤非法值”是校验
- “补出 AI 没选的域”已经不是校验，而是在替 AI 扩写本场考纲
- 这会直接改变后续 `ledger`、知识域覆盖、出题方向

建议：

- 保留“过滤非法域”
- 删除“按最少 5 个知识域自动回填”
- 如果 planner 输出不足，要么拒收，要么显式降级成更小考纲，不能擅自加考点

### 4. `AiOutputContractValidator` 在推断 `interviewAction`，已经越过“校验”边界

证据：

- `backend/src/main/java/com/a05/aiinterview/ai/contract/AiOutputContractValidator.java:91-140`

现状：

- `interviewAction` 非法时，不是直接拒收或降级
- 代码会根据 `nextQuestionType/nextFocus/expectedAnswerPoints` 去推断它应该是 `CONTINUE` 还是 `WRAPUP`
- 还会补 `candidateStrategies` 和 `finalDecision`

问题：

- 这不是“格式修正”，而是在程序侧补写 AI 意图
- 用户要求的是：程序可以拒收、降级、兜底，但不应擅自改写 AI 语义结果
- 这里最明显的越界点就是 `inferInterviewAction()`

建议：

- 保留字段合法性校验
- 非法就直接失败或降级到明确 fallback
- 不要再从其他字段反推一个新的 AI 决策

### 5. 题型存在两套枚举体系，主链路靠运行时映射硬接

证据：

- `backend/src/main/java/com/a05/aiinterview/ai/dto/EvaluationDecisionOutput.java`
- `backend/src/main/resources/prompts/evaluation-decision.md`
- `backend/src/main/java/com/a05/aiinterview/interview/service/QuestionStreamService.java:1127-1136`
- `backend/src/main/java/com/a05/aiinterview/interview/entity/InterviewQuestion.java`

现状：

- `evaluation-decision` 输出：`THEORY / PROJECT / SCENARIO / SOFT_SKILL`
- 题目实体和出题 prompt 使用：`PRINCIPLE / PROJECT_DEEP_DIVE / SCENARIO / BEHAVIORAL`
- `QuestionStreamService.mapQuestionTypeForStorage()` 专门做了一层映射

问题：

- 这说明新旧契约并没有统一，系统只是用 mapping 暂时粘住了
- 后续任何一侧扩字段或改语义，另一侧都可能出现静默错配

建议：

- 统一成一套 canonical question type
- evaluation、question generation、落库、前端展示全部使用同一套枚举

### 6. SSE `done` 事件只给 `questionId`，前端被迫伪造下一题元数据

证据：

- `backend/src/main/java/com/a05/aiinterview/interview/dto/SseDoneEvent.java:14-30`
- `frontend/src/components/InterviewPage.vue:2045-2059`

现状：

- 后端 `done` 事件只返回 `questionId`
- 前端收到后自己构造下一题对象，并硬编码：
  - `questionType: 'PRINCIPLE'`
  - `domainName: ''`
  - `targetSkill: ''`

问题：

- 这会让前端持有的题目元数据不再等于后端真实落库结果
- 下一题如果实际是 `PROJECT_DEEP_DIVE` / `BEHAVIORAL`，前端仍会把它当 `PRINCIPLE`
- 专业模式下 ASR 停顿阈值取的是当前题 `questionType`，这里会直接用错题型

建议：

- `done` 事件返回完整 question snapshot
- 或流结束后前端再调一次后端接口拿权威题目对象
- 前端不要本地硬编码题型和领域

### 7. 会话详情只返回首题快照，流式生成后的当前题没有权威读取入口

证据：

- `backend/src/main/java/com/a05/aiinterview/interview/service/InterviewService.java:137-140`
- `backend/src/main/java/com/a05/aiinterview/interview/service/QuestionStreamService.java:656-696`

现状：

- `getSessionDetail()` 在 `in_progress` 时只把 `firstQuestionJson` 塞给前端
- 后续流式生成新题时，只更新了 `currentQuestionNo`
- 没有同步更新当前题 snapshot

问题：

- 中途刷新页面或多端恢复时，前端拿不到当前题，只能拿到第一题
- 这会让会话状态和题目状态脱节

建议：

- session 里维护当前题快照，或者提供单独的 `GET current-question` 接口
- 不要把“首题快照”当成整个面试会话的长期 current question 来源

## P1 问题

### 8. `skip-and-next` 走的是硬编码伪决策，不是主链路

证据：

- `backend/src/main/java/com/a05/aiinterview/interview/service/InterviewSkipService.java:55-99`

现状：

- 跳题不会经过 `evaluation-decision`
- 后端直接造一个 `EvaluationDecisionOutput`
- 默认下一题类型固定成 `THEORY`
- `nextFocus` 直接取当前题的 domainName

问题：

- 这是一条和主链路完全不同的决策路径
- 一旦主链路契约变了，skip 链路很容易继续按旧逻辑跑
- 跳题后的下一题质量也会明显弱于主链路

建议：

- 要么把 skip 收口进统一决策服务
- 要么明确把它当“程序降级链路”，并在命名和日志里与正常 AI 决策严格区分

### 9. 单题模式至少保留了三份实现，属于明显的旧链路残留

证据：

- `backend/src/main/java/com/a05/aiinterview/interview/dto/CreateInterviewRequest.java`
- `backend/src/main/java/com/a05/aiinterview/interview/service/InterviewService.java:93-98`
- `backend/src/main/java/com/a05/aiinterview/interview/service/InterviewService.java:150-245`
- `frontend/src/App.vue:1038-1050`
- `frontend/src/components/InterviewPage.vue:1167-1188`

现状：

- 后端支持 `singleQuestion*` 字段创建单题会话
- 前端问答库“重做”又直接走 `startSingleQuestionInterview()` 的纯本地模式
- 主面试链路还有自己独立的 `createInterview -> attempts -> SSE`

问题：

- 这已经不是一个链路的分支，而是三套实现
- 后续任何一处改契约，另外两处都可能继续按旧逻辑跑

建议：

- 统一单题练习入口
- 要么完全接入主链路
- 要么明确删除不再使用的本地单题模式和后端单题特殊字段

### 10. 专业模式仍允许切回文字输入，和“仅语音”规则冲突

证据：

- `frontend/src/components/InterviewPage.vue:462-483`
- `frontend/src/components/InterviewPage.vue:516-533`
- `frontend/src/components/InterviewPage.vue:2194-2204`

现状：

- UI 直接暴露“文字/语音”切换按钮
- `setInputMode('text')` 也是真可用的
- 专业模式只是启动时默认选语音，并没有真正锁死文本输入

问题：

- 这和当前已拍板的“专业模式仅语音输入”是冲突的
- 一旦用户在专业模式下切到文字，前后端对回答形态、停顿分析、ASR 字段的假设都会失真

建议：

- 专业模式隐藏文本输入切换
- 设备失败时应提示用户重试/退出，而不是静默降级到文本

### 11. `QuestionStreamService` 找不到领域时会退回 syllabus 第一个 domain，容易写错题目归属

证据：

- `backend/src/main/java/com/a05/aiinterview/interview/service/QuestionStreamService.java:1084-1113`

现状：

- `nextFocus` 匹配不到明确领域时，`resolveRelatedDomain()` 会直接回退到第一个 domain

问题：

- 这会把真实没有收敛到某个 domain 的题，强行落到一个无关 domain 下
- 进而污染题目详情、报告分域统计、后续 hint 和 question review

建议：

- 匹配不到就保持 domain 为空
- 不要默认拿第一个 domain 充数

### 12. 出题流重建下一题计划时只保留了二元动作，丢掉更细粒度决策

证据：

- `backend/src/main/java/com/a05/aiinterview/interview/service/QuestionStreamService.java:554-574`

现状：

- 从 attempt 的 `evaluationJson` 取下一题计划时，`interviewAction` 被硬编码成 `"CONTINUE"`
- `candidateStrategies`、`finalDecision` 等信息没有继续往下游透传

问题：

- 即使未来 `evaluation-decision` 真正区分 `followup/probe/rescue/broaden`，流式出题链路也会先把它压扁
- 新“弱控制”设计的细粒度动作，在这里已经被丢了

建议：

- 统一定义决策结果的 canonical 结构
- question generation 直接消费该结构，而不是在中间再手工裁切一版

## 建议的清理顺序

### 第一批，必须先做

1. 删除前端 `evaluationSignal` 兼容和相关测试。
2. 删除前端基于 `decision` 的本地打分/本地总分/随机 `beatPercent`。
3. 停止 `PlannerDomainNormalizationService` 自动回填 planner 未输出的 domain。
4. 停止 `AiOutputContractValidator` 推断 `interviewAction`。
5. 统一 question type 枚举，删掉 `mapQuestionTypeForStorage()` 这类过渡层。

### 第二批，紧接着做

6. 让 SSE `done` 事件返回完整题目快照，前端不再本地伪造下一题对象。
7. 给会话提供当前题权威读取能力，修掉“只保存首题快照”的设计。
8. 把 `skip-and-next` 收口到统一决策链，或者显式标记成降级链路。

### 第三批，清旧链

9. 删除前端本地单题模式，统一走后端会话。
10. 清掉后端 `singleQuestion*` 特殊入口，或明确保留唯一实现。
11. 专业模式锁死语音输入，失败时不要自动回文字。

## 总结

现在最大的技术债不是某个接口报错，而是“系统已经说自己切到新链路了，但内部仍然允许旧语义、旧旁路、旧造值方式继续活着”。

这会造成三个后果：

1. AI 的原始判断在多个层面被程序重新解释甚至改写。
2. 前后端看到的“当前题/当前决策/当前分数”并不一定来自同一真相源。
3. 旧链路虽然不显眼，但一直在给新链路埋兼容性雷。

如果这次不把旧旁路和语义补写层彻底删掉，后续每次调 prompt、调 DTO、调状态账本，都会继续出现“明明改了新链路，线上却还是旧行为”的问题。
