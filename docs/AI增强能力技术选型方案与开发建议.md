# AI 增强能力技术选型方案与开发建议

## 1. 文档目标

本文面向当前 `AI 模拟面试系统` 的下一阶段建设，重点分析以下 7 类能力的技术选型与落地建议：

1. `RAG` 检索增强
2. 大模型接入与多模型路由
3. 流式输出
4. 语音分析
5. `AI` 面试官形象
6. 语音播报
7. 学习资源推送

本文不是脱离现状的理想化设计，而是基于当前项目已经具备的 `Spring Boot + Spring AI + MySQL + Redis + WebFlux SSE` 基础能力，给出一套适合分阶段推进的增量方案。

---

## 2. 当前基础与关键判断

结合现有代码和文档，当前项目已经具备以下基础：

- 已有统一 `AiClient` 抽象，支持 `Planner / Evaluation / QuestionGeneration / ReportGeneration`
- 已接入 `Spring AI ChatClient`
- 已有逐题提交主链路 `AnswerSubmitService`
- 已有 `SSE` 接口，但当前是"数据库已生成题目的打字机推送"，还不是真正的模型增量流
- `RAG` 入口已预留，但仍是 `stub`
- 当前技术栈以 `Java` 单体为主，适合继续保持核心编排在后端统一收口

基于以上现状，建议采用以下总原则：

- 核心面试链路继续由 `Java` 服务统一编排，不建议过早拆分过多微服务
- 文本类能力优先复用当前 `Spring AI` 能力栈，避免重复封装
- 音频分析能力建议边界清晰，必要时拆分为独立 Python 服务
- 流式文本与语音/形象驱动不要混为一层协议，文本优先 `SSE`，实时音视频优先 `WebSocket`
- 先做"可上线的稳定版本"，再做"高拟真数字人版本"

---

## 3. 总体技术路线结论

推荐采用"两层能力架构"：

### 3.1 核心编排层

由当前 `backend` 继续承担：

- 面试会话生命周期管理
- 逐题评估与下一题决策
- `RAG` 检索编排
- 模型路由与审计日志
- 流式文本输出聚合
- 语音最终稿入库与结果回放

### 3.2 实时交互层

面向更强交互体验，逐步增加：

- 前端直连云厂商实时 `ASR`
- 前端通过 `SSE/WebSocket` 接收题目文本和播报事件
- `TTS` 服务生成音频流
- 数字人前端根据音频时间轴或音素驱动口型
- 如需更强声学分析，再接入独立音频分析服务

## 4. 分能力技术选型建议

## 4.1 RAG 检索增强

### 4.1.1 目标

在出题、追问、反问纠偏、报告生成等环节引入外部知识，解决"题目泛化但不够贴岗位、不够贴知识域、不够贴评分标准"的问题。

### 4.1.2 适合本项目的知识源

建议优先建设以下三类知识库：

- `岗位知识库`：岗位题纲、知识域说明、考察点、评分锚点
- `面试题知识库`：高质量题目、追问模板、反例、常见误区
- `简历/项目知识库`：候选人项目经历切片、项目关键词、可深挖点

后续再增加：

- `业务规范知识库`：面试流程策略、提示词模板、评分口径
- `行业知识库`：中间件、数据库、系统设计案例资料

### 4.1.3 向量库选型对比

#### 方案 A：`Redis Vector Store`（不推荐）

优点：

- 当前项目已有 `Redis`，零新增基础设施
- 接入成本最低

不足：

- 向量检索是 Redis 的附加功能，不是核心设计目标
- 不支持复杂 metadata 过滤组合
- 大规模检索性能不可预期
- 比赛评审场合被认为是"凑合方案"，技术印象分低

适用判断：

- 不推荐作为向量库选型，`Redis` 继续用于缓存和分布式锁等原有职责

#### 方案 B：`pgvector`（不推荐，除非迁移数据库）

优点：

- 数据和向量统一落在 PostgreSQL，ACID 事务保证，架构极简
- Spring AI 原生支持 `PgVectorStore`
- SQL 层面可做结构化字段过滤 + 向量相似度联合查询

不足：

- 当前项目数据库是 `MySQL`，引入它意味着完整的数据库体系迁移
- 需要重新验证所有 MyBatis Plus 兼容性，风险不可控

适用判断：

- 仅在明确计划将整体数据库迁移到 `PostgreSQL` 时考虑

#### 方案 C：`Qdrant`（推荐）

优点：

- 专为向量检索设计，性能和过滤能力强
- Docker 单容器一条命令启动，与 MySQL 完全独立、互不干扰
- Spring AI 原生支持 `QdrantVectorStore`，只需改依赖和配置，业务代码不动
- 自带 Dashboard 可视化界面，比赛演示友好
- 开源免费，社区活跃
- 支持丰富的 payload 过滤，便于按 `domainCode/questionType/difficulty` 精确召回

不足：

- 新增一个独立进程，多一个组件需要维护
- 与业务数据库之间无事务保证，一致性由应用层处理

接入方式：

```bash
# 启动 Qdrant
docker run -d -p 6333:6333 -p 6334:6334 qdrant/qdrant
```

```xml
<dependency>
    <groupId>org.springframework.ai</groupId>
    <artifactId>spring-ai-qdrant-store-spring-boot-starter</artifactId>
</dependency>
```

```yaml
spring:
  ai:
    vectorstore:
      qdrant:
        host: localhost
        port: 6334
        collection-name: interview_knowledge
        initialize-schema: true
```

适用判断：

- 当前项目的最佳选择：保留 MySQL 不动，Qdrant 专门处理向量检索

#### 方案 D：`Milvus`（不推荐）

优点：大规模分布式向量检索能力最强。

不足：依赖 etcd、MinIO 等多个组件，部署复杂，比赛项目完全用不到这个量级，得不偿失。

#### 方案 E：`Elasticsearch`（不推荐）

优点：支持全文检索 + 向量混合检索，知名度高。

不足：JVM 资源消耗大，向量检索只是附加能力，技术栈偏重，除非项目有明确的全文检索需求否则不引入。

### 4.1.4 推荐结论

**推荐选型：`Qdrant`**

- 保留 MySQL 处理所有业务数据，不做任何数据库迁移
- 新增 Qdrant 专门处理向量检索，两者独立运行互不干扰
- 保留 `RagRetrievalService` 抽象层，后续如有需要可平滑切换底层实现

### 4.1.5 检索策略建议

不要只做"query -> topK 文本拼接"，建议至少做到以下结构：

1. 查询改写
2. 多路召回
3. 轻量重排
4. 结果分组注入 Prompt

建议的召回维度：

- 按 `domainCode`
- 按 `questionType`
- 按 `targetDepth`
- 按 `focusPoint`
- 按 `resume/project` 关键词

建议的 metadata：

- `knowledge_type`
- `domain_code`
- `question_type`
- `difficulty`
- `source`
- `project_id`
- `position_code`
- `version`

### 4.1.6 开发建议

- 新增 `RagRetrievalService`，统一封装召回、过滤、降级逻辑
- 新增 `KnowledgeIngestionService`，负责切片、向量化、metadata 入库
- `AnswerSubmitService` 中 Step6 正式接入检索
- 检索失败时必须降级，不阻断主链路
- 把检索命中结果写入 `ai_invocation_logs.retrieval_context_json`
- 先不做复杂 Agent 化检索，优先保证稳定、可解释、可追踪

### 4.1.7 推荐实施顺序

1. 先做岗位知识库和评分锚点知识库
2. 再做题库和追问模板知识库
3. 最后再做简历项目知识库

## 4.2 大模型接入与多模型路由

### 4.2.1 目标

解决三个核心问题：

- 质量和成本平衡
- 不同环节模型能力差异化
- 避免被单一厂商强绑定

### 4.2.2 当前基础判断

项目已经有：

- `AiClient` 抽象层
- `OpenAiClient`
- `MockAiClient`
- `Spring AI ChatClient`

这说明当前架构已经具备"继续做多模型路由"的良好基础，不建议推倒重来。

### 4.2.3 推荐模型分层

建议至少分为三类模型：

#### A. 主决策模型

用于：

- `Planner`
- `EvaluationDecision`
- `ReportGeneration`

要求：

- 推理稳定
- JSON 输出稳定
- 指令遵循好

建议：

- 使用质量优先模型
- 统一走结构化输出

#### B. 出题流式模型

用于：

- 下一题生成
- 追问生成
- 口语化改写

要求：

- 首字延迟低
- 流式体验稳定
- 成本可控

建议：

- 使用低时延模型
- 允许与主决策模型分离

#### C. 轻量辅助模型

用于：

- query rewrite
- 标签提取
- 简单摘要
- 文本清洗

要求：

- 便宜
- 快

### 4.2.4 推荐接入方式

建议保留当前 `Spring AI` 作为统一适配层，并在业务侧增加一层 `ModelRoutingService`：

- 根据 `promptCode` 选择模型
- 根据环境切换供应商
- 根据请求类型控制超时、重试、温度
- 统一记录 `provider/model/promptVersion/token/latency`

### 4.2.5 供应商策略建议

建议采用"主供应商 + 备供应商"模式，而不是单供应商模式。

判断标准不要先看品牌，而要先看这 6 项：

1. 是否支持稳定的流式输出
2. 是否支持结构化 JSON 输出
3. 是否支持 OpenAI-compatible 或 Spring AI 友好接入
4. 是否支持国内网络环境稳定访问
5. 是否支持并发限流和配额管理
6. 是否支持审计与成本统计

### 4.2.6 开发建议

- 新增 `ModelRoutingService`
- `AiClient` 保持接口稳定，不让业务层感知供应商差异
- 把 `promptCode -> model strategy` 配成可热更新项
- 给每个核心 Prompt 加版本号
- 为 `Planner / Evaluation / Question / Report` 建立契约测试
- 对 JSON 结构化输出增加兜底修复与失败告警

### 4.2.7 推荐结论

短期最佳方案：

- 继续使用当前 `Spring AI + OpenAI-compatible` 接口形态
- 增加多模型路由而不是重写客户端
- 形成"主模型负责决策，快模型负责流式表达"的组合

## 4.3 流式输出

### 4.3.1 目标

让用户感知到"AI 面试官正在思考和提问"，而不是等整题生成完成后再一次性返回。

### 4.3.2 当前问题

当前 `SSE` 只是把数据库已存在题目文本逐字符推送，本质上是"伪流式"，对体验有帮助，但并不具备以下能力：

- 实时首字返回
- 生成中打断
- token 级错误恢复
- 与语音播报、数字人联动

### 4.3.3 协议选型建议

#### 一期：文本流式继续用 `SSE`

原因：

- 当前后端已经有 `Flux<String>`
- 前端实现成本低
- 对"下一题逐步显示"场景足够

#### 二期：实时互动升级到 `WebSocket`

用于：

- 实时 `ASR`
- 语音播报控制
- 数字人口型驱动事件
- 打断、取消、重连

### 4.3.4 推荐协议拆分

建议不要试图用一个通道承载所有能力，而是拆成两类：

- `SSE`：文本题目流、状态通知、轻量事件
- `WebSocket`：语音、打断控制、数字人动作事件

### 4.3.5 事件协议建议

建议把当前单纯 `Flux<String>` 升级为结构化事件流：

- `start`
- `delta`
- `done`
- `error`
- `usage`
- `tts_ready`（携带音频片段 ID 和时间轴）
- `tts_done`

这样后续就能平滑接入前端播报和数字人联动，而不是再重做协议。

### 4.3.6 开发建议

- 改造 `InterviewService.streamQuestion(...)`
- 不再读取"已存量题目文本"，而是直接透传 `aiClient.callQuestionGenerationStream()`
- 题目生成完成后再统一落库最终版本
- 为每次生成分配 `generationId`
- 增加断线重连策略和幂等控制
- 增加"用户跳过播报/中断生成"能力

### 4.3.7 推荐结论

推荐路线：

- 现在立刻把文本流改成真正的模型流式 `SSE`
- 语音和数字人阶段再引入 `WebSocket`

## 4.4 语音分析

### 4.4.1 目标

语音分析不要只理解为"语音转文字"，建议拆成两层：

- `ASR`：把语音转成结构化文本
- `Speech Analytics`：分析语速、停顿、口头禅、情绪波动、表达稳定性

### 4.4.2 推荐能力拆分

#### A. 实时转写

用于面试过程中：

- 实时字幕
- 最终答题文本
- 停顿与断句识别

#### B. 非实时分析

用于面试结束后：

- 语速统计
- 长停顿次数
- 口头禅占比
- 句长分布
- 情绪和能量稳定性

### 4.4.3 技术选型建议

#### 实时 `ASR`

推荐优先使用成熟云厂商实时语音识别服务，而不是首期自建。

原因：

- 延迟更低
- 中文识别更成熟
- 有时间戳、增量修正、分段能力
- 前端可直连，降低后端音频中转压力

选择标准：

- 是否支持实时 WebSocket
- 是否返回 `is_final`
- 是否支持时间戳和分段结果
- 是否支持中文技术口语场景
- 是否支持长语音稳定识别

#### 声学分析

推荐作为独立能力看待，不建议首期塞进当前 Java 主服务。

建议方式：

- 首期：基于 `ASR` 时间戳先做弱声学指标
- 二期：增加 Python 音频分析服务

适合单独放到 Python 服务的原因：

- 音频特征提取生态更成熟
- 适合接 `Whisper/FunASR/pyannote/librosa`
- 便于后续加说话人分离、韵律分析、情绪分析

### 4.4.4 推荐架构

实时面试阶段：

1. 前端采集麦克风音频
2. 前端直连云厂商实时 `ASR`
3. 前端展示中间字幕
4. 最终 `is_final=true` 文本提交给后端 `submitAttempt`

异步分析阶段：

1. 前端或后端保存音频文件
2. 任务投递到音频分析服务
3. 输出表达分析结果
4. 报告生成时引用

### 4.4.5 停顿打标策略（ASR 声学特征内联化）

纯文本大模型无法直接感知音频时间轴，建议在前端完成"声学特征 → 语义 Token"的降维转换。

**核心机制**：前端维护 ASR 时间轴，当某个分段的 `pause_ms_after` 超过阈值时，在最终答题文本中对应位置插入 `[停顿 Xs]` 标签，使大模型能够直接感知候选人的犹豫与卡壳：

```
原始 ASR 分段：
  "我先做容量估算"  pause_ms_after=300
  "再调整线程池"    pause_ms_after=2800
  "用FIFO策略"     pause_ms_after=100

打标后文本：
  "我先做容量估算，再调整线程池 [停顿 2.8s] 用FIFO策略"
```

**阈值配置**：停顿阈值不能硬编码，须按 `questionType` 分档，建议：

| questionType | 停顿阈值 | 判断依据 |
|---|---|---|
| `INTRO` | 2000ms | 自我介绍题不应卡顿 |
| `PRINCIPLE` | 2500ms | 原理题需要适度思考 |
| `SCENARIO` | 3000ms | 场景题允许更长的分析停顿 |
| `PROJECT_DEEP_DIVE` | 2000ms | 讲自己的项目不应频繁停顿 |
| `BEHAVIORAL` | 2500ms | 行为题需要组织语言 |

**额外计算指标**：前端在 `is_final=true` 时同步计算并上报：

- `wpm`：整体语速（词/分钟）
- `longPauseCount`：超过阈值的停顿次数
- `longestPauseMs`：最长单次停顿时长

**注意事项**：

- 连续短停顿（`<500ms` 的多次停顿）应合并处理，避免 token 过密
- 停顿 token 数量建议上限为 10 个，超过后以摘要形式输出，如 `[多次停顿，共 8 次]`
- 阈值应由服务端配置接口下发，前端启动时拉取一次缓存，不要硬编码

### 4.4.6 开发建议

- 提交协议中增加 `asrSegments`、`pauseStats`（含 `wpm`、`longPauseCount`、`longestPauseMs`）、`audioUrl`
- 答题文本 `answerText` 使用打标后的富文本，而不是原始 ASR 纯文本
- 阈值配置通过专用接口由后端下发，前端启动时拉取并缓存
- 先基于打标文本做表达流畅度指标，不建议首期做"情绪分高低影响录用"的强结论
- 报告中更适合输出"表达节奏观察"，而不是"情绪判断结论"

### 4.4.7 推荐结论

推荐方案：

- 实时转写：云厂商实时 `ASR`
- 停顿打标：前端内联化，按 `questionType` 分档阈值
- 深度声学分析：独立 Python 服务，后置异步处理

## 4.5 AI 面试官形象

### 4.5.1 目标

提升沉浸感、信任感和产品演示效果，但不让形象系统反过来拖累核心面试链路稳定性。

### 4.5.2 选型原则

数字人能力天然是"高体验、高复杂度、高成本"模块，建议分级推进。起步阶段优先选择最轻量、实现成本最低的方案，确保面试核心链路不受数字人模块影响。

### 4.5.3 三种实现路线

#### 方案 A：音量驱动动效（推荐起步方案）

特点：

- 最轻量，实现成本极低
- 无需 Live2D 授权或模型制作
- 基于 Web Audio API 实时获取麦克风/扬声器音量
- 根据分贝值驱动简单的圆形波纹、光圈扩散或头像缩放动画
- 与当前已有的麦克风测试动画完全同源，可直接复用
- 即使 TTS 时间轴解析失败也能正常工作（天然降级）

适用场景：

- 当前阶段首选，快速验证"AI 面试官在说话"的用户感知

#### 方案 B：2D 数字人（音素/时间轴驱动）

特点：

- 拟人感明显提升
- 需要 TTS 返回字词或音素时间戳
- 需要 Live2D 商业授权 + 模型制作成本
- 前端可控性较好，复杂度中等

适用场景：

- 产品进入正式演示和商用验证阶段，且已确认授权和美术预算

#### 方案 C：实时 3D/视频数字人

特点：

- 体验最好
- 成本和工程复杂度最高
- 对网络和端侧性能要求高

适用场景：

- 强展示型场景，或者明确把数字人作为核心卖点

### 4.5.4 推荐结论

推荐采用分阶段路线，起步必须从音量驱动动效开始：

- `V1`：音量驱动波纹/光圈动效 + TTS 播报（当前阶段执行）
- `V2`：2D 数字人 + 音素/时间轴驱动（确认授权预算后推进）
- `V3`：只有在商业目标明确时再考虑实时 3D 或视频数字人

V1 的降级策略：只要有声音波形，动效就响应；TTS 时间轴不可用时自动降级到纯音量驱动，不影响体验。

### 4.5.5 架构建议

不要把数字人生成为后端主链路的一部分，建议解耦：

- 后端负责输出题目文本和播报指令
- `TTS` 输出音频及时间信息
- 前端播放器驱动动效、口型、字幕

这样即使数字人模块异常，也不影响题目生成和答题提交。

### 4.5.6 开发建议

- 定义统一的 `avatarAction` 事件，V1 只用 `speaking/idle` 两个状态
- V1 直接复用麦克风测试页的 Web Audio API 分析节点
- `TTS` 结果中如果有音素或字词时间戳，优先透出给前端，为 V2 预留
- 前端数字人组件单独维护状态机，不要耦合到面试主页面业务代码
- 面试链路里始终保留"无动效降级模式"

## 4.6 语音播报

### 4.6.1 目标

把题目文本转成自然语音，让用户获得接近真人面试官的提问体验。

### 4.6.2 技术路线建议

语音播报优先选择云厂商 `TTS`，不要首期自建语音合成模型。

原因：

- 首次接入成本低
- 情感、停顿、音色能力更成熟
- 有流式合成或快速返回能力
- 商用场景稳定性更高

### 4.6.3 供应商选择标准

优先看以下能力：

1. 是否支持中文自然播报
2. 是否支持流式合成
3. 是否支持多音色和情绪控制
4. 是否支持 `SSML`
5. 是否支持字词时间戳或音素时间戳
6. 是否能与 `ASR` 同厂商打通

### 4.6.4 推荐策略

建议 `ASR` 和 `TTS` 优先选择同一供应商。

原因：

- 接口风格统一
- 鉴权统一
- 音频编解码和时间轴更容易协同
- 后续做语音中断、回声消除、全双工体验更顺

### 4.6.5 开发建议

**一期（整段合成）**：

- 文本生成完成后异步触发 `TTS`，整段合成后推送给前端
- 允许前端选择"自动播报 / 手动播放 / 静音模式"
- `TTS` 产物缓存到对象存储，对相同题目文本做短期缓存
- 为播放链路增加 `skip` 和 `interrupt` 控制

**二期（句级缓冲 Pipeline）**：

后端在读取 LLM 流式输出（`Flux<String>`）时，启用句级缓冲策略：

1. 维护一个 `StringBuilder` 缓冲区，持续接收模型增量 token
2. 遇到句末标点（`，`、`。`、`？`、`！`、`；`）时立即切断当前片段
3. 将切断的短句异步调用 TTS 接口合成音频
4. 通过 **SSE 文本事件通道** 推送文本 delta 和 `tts_ready` 事件（携带片段 ID、顺序号、时间轴）
5. 前端收到 `tts_ready` 后，通过 **独立 HTTP 音频接口** 按 ID 拉取音频片段顺序播放

Pipeline 效果：用户听第一句时，后端已在合成第二句，主观延迟趋近于零。

**通道拆分原则**：

- `SSE` 只承载文本事件和轻量控制事件，不内嵌二进制音频
- 音频通过独立 HTTP 接口按需拉取，避免 Base64 编码的 33% 体积膨胀和 SSE 大 payload 阻塞

### 4.6.6 推荐结论

推荐方案：

- `1 期`：题目生成后整段合成并播放
- `2 期`：句级缓冲 Pipeline + SSE/音频双通道
- `3 期`：和数字人口型、字幕、打断控制统一编排

## 4.7 学习资源推送

### 4.7.1 目标

学习资源推送的目标不是"给用户堆链接"，而是基于面试过程中的薄弱点、岗位方向和项目背景，向用户推荐真正可执行的后续学习内容，形成"面试评估 -> 差距识别 -> 学习建议 -> 再训练"的闭环。

### 4.7.2 能力定位

建议将学习资源推送定义为面试系统的后置增强能力，而不是主面试链路中的强依赖模块。

它主要服务三个场景：

- 面试结束后，生成个性化学习路径
- 单题答完后，对明显薄弱点给出轻量补强建议
- 用户进入个人成长页时，持续看到与岗位目标相关的学习内容

### 4.7.3 推荐内容来源

建议优先建设三类资源池：

- `结构化资源库`：八股文、技术专题、官方文档、精选文章、课程、视频、实战项目
- `题目关联资源库`：每个 `domainCode/focusPoint` 对应的补充学习材料
- `学习路径模板库`：按岗位、级别、知识域组织的学习路线

资源 metadata 建议至少包含：

- `resource_id`
- `title`
- `resource_type`
- `domain_code`
- `focus_point`
- `difficulty`
- `estimated_minutes`
- `source`
- `quality_score`
- `tags`

### 4.7.4 技术选型建议

学习资源推送本质上是"推荐系统 + 检索增强"的组合，建议分阶段建设：

#### 一期：规则推荐 + 向量召回

实现方式：

- 基于面试报告和逐题评估结果抽取薄弱点
- 用 `domainCode + targetDepth + focusPoint + wrongPattern` 生成推荐查询
- 从学习资源向量库中召回相关资料
- 再按规则做过滤和排序

优点：

- 与当前 `RAG` 基础设施复用度高
- 落地快、可解释性强
- 适合冷启动

#### 二期：规则推荐 + 向量召回 + 轻量排序模型

实现方式：

- 在召回结果基础上增加排序层
- 综合"薄弱程度、资源质量、用户目标岗位、历史点击/完成情况"计算推荐分

优点：

- 推荐结果更贴近个人差异
- 可以逐步引入用户行为反馈

#### 三期：个性化推荐系统

实现方式：

- 引入用户画像、学习历史、收藏/完成/跳过行为
- 建立长期成长画像和学习路径编排

适用判断：

- 只有在用户量和资源量达到一定规模后再投入，不建议当前阶段直接建设重型推荐平台

### 4.7.5 推荐架构建议

建议拆成四层：

- `LearningResourceRepository`：学习资源元数据与内容管理
- `LearningResourceRetrievalService`：资源召回，复用向量检索能力
- `LearningRecommendationService`：推荐排序、去重、解释文案生成
- `LearningPlanService`：把推荐结果组织成"立即补强 / 一周计划 / 长期提升"结构

这样可以保证：

- 资源管理和推荐逻辑分离
- 未来可以平滑接入行为数据排序
- 学习资源推送既能服务报告页，也能服务成长页

### 4.7.6 与当前面试系统的结合点

推荐系统不应脱离面试结果单独运行，建议重点接 4 个输入：

1. `EvaluationDecisionOutput`
2. 最终面试报告中的亮点和薄弱项
3. `RAG` 知识域与 `focusPoint`
4. 用户目标岗位、年限和目标级别

推荐输出建议分三层：

- `立即学习`：和本次薄弱点直接相关，适合 10~30 分钟补强
- `重点补齐`：按知识域给出 1~2 周的重点提升内容
- `长期进阶`：和目标岗位升级相关的系统化学习路线

### 4.7.7 召回与排序策略建议

不要只按向量相似度返回内容，建议至少做以下几步：

1. 根据面试结果抽取"薄弱点标签"
2. 基于标签做精确过滤
3. 使用向量召回相近资源
4. 根据资源质量、难度匹配、时长、是否重复学习做排序
5. 生成推荐理由

排序时建议考虑这些因子：

- 薄弱点匹配度
- 与目标岗位的相关度
- 与用户当前级别的匹配度
- 资源质量评分
- 内容新鲜度
- 学习成本
- 是否已推荐过或已学过

### 4.7.8 推荐结果展示建议

推荐结果不要只返回列表，建议结构化为：

- 推荐标题
- 推荐理由
- 预计学习时长
- 难度等级
- 资源类型
- 适合的学习顺序

示例展示形态建议：

- 报告页：每个薄弱知识域后给出 2~3 条高价值资源
- 成长页：按"本周优先学习 / 后续进阶学习"展示
- 复盘页：按"本题为什么答得不够好 -> 建议补什么"展示

### 4.7.9 开发建议

- 复用 `RAG` 的向量化与检索基础设施，不单独重复建设一套检索底座
- 新增 `learning_resources` 数据表或独立资源中心
- 建立资源标准化入库流程，保证标题、标签、知识域、难度可控
- 在报告生成后异步触发学习资源推荐，不阻塞主报告链路
- 推荐结果单独缓存，避免每次打开报告页都重新实时计算
- 推荐理由要可解释，避免只输出"为你推荐"

### 4.7.10 推荐结论

推荐路线：

- `一期`：基于面试评估结果做规则推荐 + 向量召回
- `二期`：增加轻量排序层和学习计划编排
- `三期`：引入用户行为反馈，演进为个性化成长推荐

## 5. 推荐的总体系统形态

## 5.1 一期推荐架构

- 后端：`Spring Boot` 统一编排
- 文本模型：`Spring AI + 多模型路由`
- 向量库：`Qdrant`（Docker 单容器，与 MySQL 独立部署）
- 文本流：`SSE`
- 实时转写：前端直连云厂商 `ASR`
- 语音播报：云厂商 `TTS`（整段合成）
- 数字人：音量驱动波纹动效（复用麦克风测试组件）
- 学习资源推送：规则推荐 + 向量召回

这是当前项目投入产出比最高、与现有代码最匹配的路线。

## 5.2 二期演进架构

- 向量检索升级为混合召回 + 轻量重排
- TTS 升级为句级缓冲 Pipeline + SSE/音频双通道
- 引入 `WebSocket` 处理语音和数字人事件
- 增加独立 Python 音频分析服务
- 数字人从音量动效升级为 2D 数字人驱动
- 学习资源推荐升级为轻量个性化排序

## 5.3 不建议当前阶段做的事情

- 不建议用 `Redis` 做向量库（向量检索用 Qdrant，Redis 继续只做缓存）
- 不建议首期直接上 Milvus 等重型分布式向量平台
- 不建议首期自研 `ASR/TTS`
- 不建议首期做实时视频数字人或 Live2D（先验证音量动效价值）
- 不建议把音频处理逻辑全部塞进当前 Java 主服务
- 不建议为了接语音而推倒当前 `SSE + Spring AI` 架构
- 不建议 TTS 音频通过 SSE Base64 内嵌下发

## 8. 风险与注意事项

## 8.1 产品风险

- 数字人很容易"炫技大于价值"，导致研发投入失衡
- 语音情绪分析如果解释过重，容易造成评估争议
- `RAG` 如果知识源质量差，反而会拉低出题质量
- 学习资源推荐如果不够贴薄弱点，会让用户感知为"泛推荐"

## 8.2 技术风险

- 流式文本、`TTS`、数字人三者联动后，链路复杂度会显著上升
- 多模型并行后，日志、限流、成本控制必须同步加强
- 音频文件存储、带宽和回放策略要提前设计
- 学习资源库如果缺少统一标签体系，后续推荐质量会迅速劣化

## 8.3 合规风险

- 语音和面试数据属于敏感数据，必须明确存储周期和脱敏策略
- 录音、转写、报告内容需要明确用户授权
- 第三方模型和语音厂商的数据合规边界要提前确认

---

## 9. 最终推荐结论

如果以"3 个月内做出稳定、可演示、可继续迭代的 AI 面试增强版"为目标，推荐路线如下：

1. `RAG`：向量库选用 `Qdrant`，Docker 单容器部署，保留 MySQL 不动，重点建设岗位知识库和评分锚点知识库
2. 大模型：保留当前 `Spring AI` 架构，增加 `ModelRoutingService` 做多模型路由
3. 流式输出：先把现有 `SSE` 升级为真正的模型增量流
4. 语音分析：实时 `ASR` 用云厂商，停顿打标在前端实现，深度声学分析放到独立 Python 服务
5. AI 面试官形象：先从音量驱动动效起步，不要一上来就做 Live2D 或重型数字人
6. 语音播报：优先接云厂商 `TTS`，一期整段合成，二期升级为句级缓冲 Pipeline
7. 学习资源推送：优先复用 `RAG` 底座，先做面试报告驱动的规则推荐，再逐步演进到个性化推荐

这条路线的核心优势是：

- 与当前项目现状兼容
- 能较快上线
- 后续有清晰演进空间
- 能把真正影响面试质量的能力和提升体验的能力分阶段拆开
