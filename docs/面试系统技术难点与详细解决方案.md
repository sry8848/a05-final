# 面试系统技术难点与详细解决方案

## 1. 文档目的

本文面向比赛材料中的“技术难点与问题解决”部分，聚焦当前仓库中已经落地的 6 个核心问题：

1. 面试节奏控制与考察覆盖的平衡
2. AI 决策不可信时的系统可控性
3. 跨场次去重与个性化增量训练
4. 用状态账本驱动连续面试
5. 实时面试体验的工程化落地
6. 用受控 Hybrid RAG 实现下一题检索注入

本文只描述当前工作区中已经存在的实现，不写未来设想，不把 Prompt 口号当成解决方案。

## 2. 问题一：如何在“真实面试节奏”和“完整能力覆盖”之间取得平衡

### 2.1 难点说明

AI 面试最常见的失败方式有两种：

- 完全放开给模型自由追问，导致它围绕某一个点不断深挖，整场面试失衡
- 为了保证覆盖面，强行按固定轮次和固定题型轮询，结果像刷题系统，不像真实面试

因此，真正的难点不是“让 AI 多问一些题”，而是让系统在下面三件事之间同时成立：

- 面试过程要像真实面试一样自然推进
- 整场面试要覆盖足够多的可判分信息
- 不同资历候选人要有不同的深度和节奏

### 2.2 简单方案为什么不够

如果只靠 Prompt 里写“请控制节奏、不要重复追问”，模型无法稳定遵守，尤其在连续多轮问答后，很容易出现：

- 某个理论点被反复验证，信息增益越来越低
- 项目题问得太少，缺少真实性和工程画像
- 理论、项目、场景、行为四类题型比例失衡
- 实习生和中高级候选人得到近似长度、近似强度的面试流程

这种方案表面上灵活，实际上不可控。

### 2.3 解决方案

我们把“节奏控制”从 Prompt 经验判断下沉成运行时规则，用“策略池 + 配额限制 + 资历分层”共同控制面试推进。

第一层是经验等级画像。系统会根据 `INTERN`、`FRESH_GRAD`、`JUNIOR`、`MIDDLE`、`SENIOR` 为候选人设置不同的：

- 总题量上限 `max_questions`
- 同一点连续追问上限
- 同知识域连续追问上限
- 同项目连续追问上限
- 理论题、项目题、场景题、行为题各自的总量上限

第二层是动作策略池。系统不会让模型直接自由生成“下一步怎么问”，而是先由后端构建当前可用的策略集合，再把这个集合交给模型做选择。对于理论题、项目题、场景题、行为题，系统分别定义了“验证、变式、同域平移、项目还原、项目压测、切换项目、进入新题型、结束面试”等策略。

第三层是运行时过滤。策略不是一直都可选，而是要经过合法性筛选：

- 当前题型是否允许使用该策略
- 当前上下文是否满足前置条件
- 是否存在项目上下文
- 是否已经触碰某类配额上限

这样一来，模型仍然能根据回答质量做动态追问，但只能在“当前场景下合法且尚未超限”的空间里行动。

### 2.4 实现落点

- `InterviewPacingSupport` 负责不同经验等级下的题量与配额真源
- `StrategyCatalog` 负责定义全部策略及其语义
- `AvailableStrategyAssembler` 负责结合上下文、前置条件与配额筛出当前合法策略池
- `EvaluationDecisionInput.availableStrategies` 负责把当前可选动作注入给模型

### 2.5 方案效果

这套设计解决的不是“题目够不够多”，而是“整场面试是否形成有节奏的能力画像”。它让系统同时具备两种能力：

- 保留 AI 动态追问的灵活性，而不是把面试写死成固定脚本
- 保证整场面试不会失控，避免过度深挖、题型失衡和资历不匹配

## 3. 问题二：如何在 AI 决策不稳定的前提下保证系统仍然可控

### 3.1 难点说明

AI 即使被要求输出结构化 JSON，也不代表这个 JSON 一定能直接执行。常见风险包括：

- 输出不存在的策略编码
- 缺少下一题焦点等关键字段
- 在应该结束面试时仍带着继续追问字段
- 在需要指定知识域时没有给出目标知识域
- 给出一个理论上可读、工程上不可执行的下一步动作

如果系统直接信任模型原始输出，那么整个面试引擎就会退化成“概率性工作”。

### 3.2 简单方案为什么不够

只做一次 JSON 解析和字段非空判断是不够的。因为模型输出的真正问题并不只在格式层，而在“是否符合当前面试上下文”的语义层。

例如，一个策略字段即使长得像合法编码，也可能根本不在当前可用策略池里；又例如，模型即使输出了结束动作，也可能同时携带了不应该继续存在的追问字段。这类错误不做运行时治理，就会直接传导到下一题生成链路。

### 3.3 解决方案

我们把 AI 决策定位为“建议”，而不是“可直接执行的命令”，并为此设计了多层治理链路。

第一层是输出契约清洗。模型返回 `evaluation_decision` 结果后，系统先对字符串、列表、检索字段做基础清洗，去掉空值、重复值和明显脏数据，避免无意义噪声继续向后传播。

第二层是决策合法性校验。`DecisionExecutionPlanBuilder` 会检查：

- 当前动作是否是合法动作
- 策略编码是否属于当前策略池
- `nextFocus` 是否缺失
- 需要目标知识域时是否正确提供
- 结束面试时是否仍然夹带继续追问字段

只有通过这一层校验，系统才会构建真正可执行的 `DecisionExecutionPlan`。

第三层是修复模式。如果原始决策未通过校验，系统不会直接失败，而是进入 `DecisionRepairOrchestrator`。修复模式会把原始失败输出、验证错误、当前可用策略重新打包给模型，请它在约束下重做一次决策。同时系统会对原始策略编码做脱敏，避免模型简单复读之前的错误答案。

第四层是系统兜底。如果修复仍然失败，系统不再继续信任模型，而是由 `SystemFallbackPlanBuilder` 生成保底执行计划。这样即使模型短时不稳定，主流程仍能继续。

第五层是执行链路隔离。下一题生成链路不会直接读取模型原始输出，而只读取最终落库的 `effectiveDecisionPlan`。这意味着原始 AI 输出只保留审计价值，不直接拥有执行权。

### 3.4 实现落点

- `AiOutputContractValidator` 负责第一层输出清洗
- `DecisionExecutionPlanBuilder` 负责第二层语义合法性校验
- `DecisionRepairOrchestrator` 负责第三层修复
- `SystemFallbackPlanBuilder` 负责第四层保底计划
- `AnswerSubmitService` 负责串联“校验 -> 修复 -> 兜底 -> 写入 effectiveDecisionPlan”

### 3.5 方案效果

这套机制的核心价值是：系统稳定性不建立在“希望模型每次都发挥稳定”这种脆弱前提上，而建立在“即使模型不稳定，系统仍然可控”的工程前提上。


## 4. 问题三：如何避免多次模拟面试反复考到同一批内容

### 4.1 难点说明

模拟面试系统如果只关注单场体验，很容易忽略一个更深层的问题：用户不是只面一次。只要用户愿意反复训练，系统就必须解决跨场次重复考察的问题。

如果每次都围绕同一个知识点、同一段项目、同一个项目切入口继续追问，那么用户看到的只是不同题面，实际训练收益并没有增加。

### 4.2 简单方案为什么不够

常见的简单做法是：

- 只在本场面试内做去重
- 只避免题面完全一样
- 靠 Prompt 提醒模型“尽量不要重复”

这些方案都不够，因为面试重复真正发生的层次往往不是题面，而是考察点和入口点。哪怕问题换了说法，只要仍然在考察同一知识点、同一项目链路，用户得到的仍然是低增益训练。

### 4.3 解决方案

我们把历史面试信息正式纳入 planner 输入，让系统在规划阶段就知道“哪些内容以前已经问过”，而不是等题生成出来后再被动修补。

首先，系统会把历史面试中已经覆盖的知识点、已经讨论过的项目或实习经历、每段经历曾经采用过的切入点、以及过去表现出的强弱项，整理成结构化历史信息输入给 planner。

其次，`PlannerHistoryDedupService` 在 planner 输出之后会做两层去重：

- 知识点 deny set：过滤历史已覆盖知识点，避免新考纲继续沿用旧焦点
- 项目入口阻断：对于历史已经从某个入口深入过的项目，新一轮面试会优先改走其他技术钩子

最后，系统不会简单删掉重复项后就结束，而是会尝试回补新的焦点：

- 如果某个知识域的原始焦点被过滤后仍有剩余，就直接保留剩余焦点
- 如果全部被过滤，则从岗位知识域描述中构造候选后备焦点
- 如果后备焦点仍不可用，才退回到最小保留项，避免 planner 结果变成空计划

因此，这不是“去重删除”，而是“去重后重建一个仍然可问的新计划”。

### 4.4 实现落点

- `PlannerInput.historyInterviews` 承载历史面试摘要
- `PlannerHistoryDedupService` 负责知识点 deny set 与项目入口去重
- `PlannerHistoryBuilderService` 负责构建跨场次项目身份与切入点信息
- `PlannerOrchestrationService` 在 planner 之后、写入 syllabus 之前执行去重整理

### 4.5 方案效果

这套方案让系统从一次性模拟器变成了持续训练器。用户重复参加面试时，系统关注的不再是“题面换没换”，而是“这次是否新增了真正有价值的考察信息”。


## 5. 问题四：如何让面试过程成为一个连续形成能力画像的系统，而不是一串松散对话

### 5.1 难点说明

面试不是独立问题的堆叠，而是一个持续形成判断的过程。系统必须持续回答下面这些问题：

- 当前正在考察哪个知识域
- 当前焦点是什么
- 哪些知识点已经覆盖
- 哪些项目经历正在被深挖
- 已经用掉了多少追问配额
- 某个知识域当前处于未问、进行中还是已覆盖状态

如果只依赖聊天上下文和数据库中的零散记录，面试引擎会越来越难解释，也越来越难恢复。

### 5.2 简单方案为什么不够

只把每一题和每一次回答分别存表，虽然能保留历史记录，但解决不了“运行态真源”问题。系统仍然很难稳定地知道：

- 下一题应该继承哪一个当前焦点
- 某个知识域是不是已经接近问透
- 当前项目锚点是否还有效
- 某次 AI 决策失败后应该从什么状态继续

这会导致链路虽然能跑，但越来越像“拼出来的功能流”，而不是一个完整的面试引擎。

### 5.3 解决方案

我们引入了状态账本机制，把面试过程中的关键运行态显式保存为结构化状态，而不是隐式散落在聊天记录中。

创建面试时，系统会先根据 planner 结果初始化：

- `syllabus_json`
- `state_ledger_json`
- `session_skill_states`

在每次用户提交回答后，系统不会直接修改旧状态，而是先构建一份 `LedgerMutation`，把这一轮真正发生的状态变化显式表达出来，例如：

- 当前题型
- 当前知识域
- 当前焦点
- 当前项目锚点
- 下一题焦点
- 新覆盖知识域
- 新覆盖知识点
- 当前动作是继续还是结束

随后，`StateLedgerReducer` 会基于旧账本和这份 mutation 生成新的账本快照；`StateLedgerPatchService` 负责把新账本写回会话，并同步更新关系表 `session_skill_states`，保证知识域状态既能完整保留，又便于查询和统计。

此外，系统还会生成新旧账本差异，用于调试和审计。这使得每一轮状态推进都不是“黑箱变化”，而是可追踪、可解释、可回放的。

### 5.4 实现落点

- `StateLedgerInitService` 负责初始化账本
- `StateLedgerPatchService` 负责写入变更
- `StateLedgerReducer` 负责基于 mutation 生成新账本
- `StateLedgerDiffService` 负责对比旧账本和新账本
- `SessionSkillStateMapper` 负责同步知识域关系表

### 5.5 方案效果

状态账本解决的是面试系统“能不能稳定形成连续画像”的问题。它让后续的下一题生成、题型切换、知识域状态管理、报告汇总、调试排错都拥有统一状态真源。

对于比赛作品来说，这种设计说明系统不是若干 AI 接口的松散拼接，而是一个真正具备内部状态和过程控制能力的面试引擎。

## 6. 问题五：如何把“像真实面试”从文案层落实到交互体验层

### 6.1 难点说明

用户是否觉得系统像真实面试，不只取决于题目内容是否专业，还取决于交互过程是否自然。体验层最容易暴露问题的地方包括：

- 每次都要等待整题生成完才有反馈，等待感过强
- 网络波动后页面重连，前面生成的内容丢失
- 题目播报只能整段播，缺少现场感
- 语音回答只能拿到最终文本，无法分析回答节奏

如果这些问题不解决，哪怕题目本身质量还可以，用户仍然会觉得它更像聊天机器人，而不是面试系统。

### 6.2 简单方案为什么不够

最直接的方案是：

- 题目整段生成完再一次性返回
- 不做断点续传，断了就重新来
- 不做分段播报，等整段文本全部生成后统一 TTS
- 语音识别只取最终转写，不分析停顿和语速


### 6.3 解决方案

我们在交互链路上做了完整的实时化设计。

第一，题目生成采用 SSE 流式输出。`QuestionStreamService` 会把生成状态缓存到 Redis，并显式区分 `streaming`、`done`、`error` 三种状态。这样用户在等待完整题目生成前，就能逐步收到内容。

第二，系统支持断点续传。如果前端中断连接，服务端不会直接丢弃这次生成任务，而是继续后台生成并把中间片段缓存下来。用户重连后，系统会先回放缓存片段，再继续 follow 未完成部分，而不是重新出一题。

第三，题目播报采用分段 TTS。系统在流式生成过程中检测句子闭合，一旦形成完整句子，就立即触发片段音频合成，而不是必须等待整题全部完成后才能播报。这样用户感受到的是“边生成边播报”的过程，更接近真人面试官逐句发问的体验。

第四，语音输入链路不只做转文字，还做答题节奏分析。`AsrTranscriptAggregator` 在聚合最终结果时会统计：

- 语速 `wpm`
- 长停顿次数
- 最长停顿时长
- 分句级语音片段信息

这些信息为后续的答题表现评估提供了客观依据，也让系统的“语音面试”不只是输入方式变化，而是增加了行为层面的分析能力。

第五，链路具备保底能力。对于网络异常、模型服务波动等情况，系统提供回退题干生成逻辑，保证面试主流程不中断。

### 6.4 实现落点

- `QuestionStreamService` 负责 SSE 流式生成、缓存状态、断点续传和 fallback 出题
- `TtsService` 负责题目音频与分段音频合成、缓存与查询
- `AsrTranscriptAggregator` 负责句段聚合与停顿统计
- Redis 负责生成状态、分段文本、音频就绪信号缓存

### 6.5 方案效果

这套方案把“真实感”从 Prompt 层推进到了交互层。用户感知到的不再是“点一下，过一会儿返回一大段文本”，而是：

- 题目逐步出现
- 断线后可以续上
- 句子一形成就能开始播报
- 语音回答不仅被记录，还能被分析节奏

对于比赛展示来说，这一层的完成度会直接影响评委对系统成熟度的判断。

## 7. 问题六：如何让下一题既贴合当前回答语义，又稳定命中正确技术点和难度边界

### 7.1 难点说明

在面试系统里，RAG 要解决的不是“补一点背景知识”，而是“为下一题生成提供受控、可解释的检索注入”。这一点和通用问答场景有本质区别。

系统至少要同时满足四个条件：

- 能理解候选人刚才回答里的真实语义，而不是只认字面关键词
- 能稳定命中高辨识度技术术语、框架名、协议名和工程机制
- 检索结果必须服从当前题型、难度和追问方向，而不是只要“相关”就可以
- 检索出的知识材料要能直接服务下一题生成，而不是返回一堆零散文本片段

这意味着，面试场景中的检索任务本质上是一个“语义相关性 + 词法精度 + 业务约束”共同成立的问题。如果检索错了，后续生成模型即使语言能力再强，也只是在错误知识基础上组织得更流畅而已。

### 7.2 简单方案为什么不够

最直接的几种方案都站不住：

- 只靠 Prompt 让大模型根据上一轮回答“自由想一题”，问题是模型没有稳定的外部知识选择机制，容易出现追问漂移和考点失真
- 只做 dense 向量检索，虽然能覆盖改写表达和经验型描述，但对中间件名、协议名、术语缩写这类高辨识度锚点不够稳定
- 只做 sparse/BM25 关键词检索，虽然术语命中率高，但对“没说标准词、只描述现象”的回答覆盖不足
- 把 dense 分数和 sparse 分数直接线性相加，也不合理，因为两类分数来自不同机制，不在统一标度空间
- 把召回结果不加约束地全部塞给模型，同样不可控，既会放大噪声，也会削弱题型和难度边界

因此，面试系统不能把 RAG 理解为“随便加一个向量库”，而必须把它设计成一条受控的检索、融合和精排链路。

### 7.3 解决方案

我们采用的是“结构化题卡 + Query 视图拆分 + Hybrid Recall + RRF + Rerank + 业务护栏”的受控 Hybrid RAG 方案。

第一，知识单元不是文档切片，而是结构化题卡。每张题卡天然带有题目、考察意图、参考语境、关键点、误区、题型和难度信息。这样系统检索的就不是“看起来相关的一段文本”，而是“可以直接注入下一题生成的一张候选题卡”。

第二，检索意图被显式拆成不同视图，而不是混成一个字符串：

- `queryText` 表示自然语言语义查询，用于 dense 与 rerank 的主语义视图
- `keywordHints` 经过去重整理后形成 `keywordQueries/sparseQueryText`，用于 sparse/BM25 的词法锚点视图
- `questionType` 与 `difficultyHint` 不参加语义相似度计算，而是作为业务过滤条件独立生效

第三，召回层采用 dense 与 sparse 双路并行。dense 路径负责语义泛化，可以抽象为：

```text
score_dense(q, d) = sim(f_q(q), f_d(d))
```

其中 `f_q` 和 `f_d` 分别把查询与题卡映射到向量空间，`sim` 表示相似度函数。它擅长处理改写表达、经验描述和长句语义映射。

sparse 路径负责术语锚点与显式词项匹配，当前采用 BM25 风格检索，其典型形式为：

```text
score_bm25(q, d) = Σ IDF(q_i) *
                   ( f(q_i, d) * (k1 + 1) ) /
                   ( f(q_i, d) + k1 * (1 - b + b * |d| / avgdl) )
```

这一路径对协议名、中间件名、机制名和缩写词更稳定，能弥补 dense 在术语精度上的波动。

第四，双路召回后不直接拼原始分数，而采用 Reciprocal Rank Fusion（RRF）做排名融合：

```text
RRF(d) = Σ_r 1 / (k + rank_r(d))
```

RRF 只依赖各路结果中的排名，不要求 dense 与 sparse 的原始分数可比，因此更适合异构检索器融合。它会自然提高“在多路结果中都排得靠前”的候选题卡权重。

第五，融合后再做 rerank 精排。原因很明确：召回层的目标是尽量找全候选，而不是直接完成最终排序。rerank 阶段使用更强的相关性判断函数：

```text
score_rerank(q, d) = g(q, d)
```

它在小规模候选集上重新判断“哪几张题卡最适合当前这一轮追问”，从而把召回问题和最终注入问题拆开。

第六，把业务护栏放进检索链路本身，而不是只写在 Prompt 里。当前系统的关键约束包括：

- 题型硬护栏：行为题、项目题、原理题、场景题不能相互串型
- difficulty window：难度不是死卡一个点，而是在局部窗口内约束，例如目标 `L2` 允许命中 `L1/L2/L3`
- 异常降级：商业 rerank 失败时，系统回退到 fusion 排序，保证主链路不中断
- 结构化审计：记录 dense/sparse 候选量、difficulty window、生效的融合结果和最终注入结果，便于排障与回放

### 7.4 实现落点

- `RagPlanCompiler` 负责取 AI 决策中的第一个 `retrievalPlan` 编译成 `RagRetrievalRequest`，显式拆开语义视图、词法视图和业务过滤条件
- `QdrantHybridQueryExecutor` 负责执行 dense 与 BM25 双路召回，并统一叠加 `active`、`questionType`、difficulty window 等基础过滤
- `RrfFusion` 负责按纯排名做双路融合，避免不同检索器原始分数不可比的问题
- `DashScopeRagRerankService` 与 `RagRerankInputBuilder` 负责融合后的二阶段精排，把最适合本轮追问的题卡排到前面
- `RagRetrievalServiceImpl` 负责串联“dense -> sparse -> RRF -> rerank -> 硬护栏 -> audit”整条检索链路
- `RagContext` 负责把最终检索材料、候选追问和结构化审计结果组织成可注入的下一题上下文

### 7.5 方案效果

这套方案解决的不是“知识库有没有接上”，而是“系统能不能在当前轮状态下，稳定拿到真正适合下一题生成的知识材料”。

它带来的实际收益有三点：

- 语义相关性和术语精度不再二选一，而是通过 Hybrid 检索互补
- 检索结果天然服从题型和难度边界，不会因为模型自由发挥而漂移
- 整条链路具备融合、精排、异常降级和结构化审计能力，生成结果不再是完全黑箱

因此，RAG 在这个系统里不是一个附属插件，而是“下一题如何被知识驱动且保持可控”的核心基础设施。

## 8. 总结

本系统在设计 AI 模拟面试链路时，重点解决的不是“怎么把大模型接进来”，而是“怎么把不稳定的大模型能力变成稳定、连续、可解释的面试系统能力”。

围绕这一目标，我们已经在当前实现中形成了六类关键方案：

- 用配额与策略池实现可控的动态面试节奏
- 用校验、修复与兜底实现 AI 决策可控
- 用跨场次去重实现持续增量训练
- 用状态账本实现连续能力画像
- 用流式交互、分段播报与语音统计实现更真实的面试体验
- 用受控 Hybrid RAG 实现语义相关、术语精确且题型与难度可控的下一题检索注入

这些方案共同构成了系统区别于普通问答式 AI 产品的核心竞争力，也是本项目在比赛材料中最值得重点展示的技术设计。
